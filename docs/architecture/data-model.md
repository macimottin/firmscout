# Data model

The authoritative definition is [`database/migrations/00001_initial.sql`](../../database/migrations/00001_initial.sql).
This document explains the reasoning, the rules the schema encodes, the tables deferred to
later migrations, and the queries the model exists to answer. Entity relationships are drawn
in [`docs/diagrams/data-model.md`](../diagrams/data-model.md).

The schema is not a neutral container. Several of FirmScout's core promises — no invented
dates, no assumed semantic versioning, immutable history, evidence on every fact, collectors
that cannot publish — are enforced here as constraints rather than left to application code
to remember. Where a rule could be expressed in SQL, it is.

## The four kinds of data

| Kind | Tables | Written by | Volume | Retention |
| --- | --- | --- | --- | --- |
| **Registry** | `vendors`, `categories`, `product_families`, `products`, `product_categories`, `product_aliases`, `product_relationships`, `sources`, `source_products`, `collector_definitions` | `firmscout registry sync` from Git | Low, human-scale | Permanent |
| **Observation** | `source_checks`, `source_artifacts`, `collector_runs`, `candidate_releases`, `validation_results` | Workers | High, machine-scale | Bounded by policy |
| **Fact** | `releases`, `release_product_mappings`, `release_notes`, `evidence` | `PublishRelease` use case only | Moderate, append-only | Permanent |
| **Platform** | `jobs`, `api_consumers`, `api_keys`, `usage_records`, `usage_aggregates`, `analytics_events`, `audit_events`, `ai_runs`, `review_items`, `product_summaries` | Various | Mixed | Mixed |

The separation is deliberate and load-bearing. Platform tables carry no foreign keys into the
fact tables, so a retention job can delete a year of usage records without any risk of
touching published history. Observation tables can be truncated in a development database
without losing the catalogue.

## Identifiers

Primary keys are `TEXT`, generated by the application's `IDGenerator` port with a type prefix
(`ven_`, `prd_`, `src_`, `rel_`, `cnd_`, `job_`, `key_`). This costs more index space than
`BIGINT` and more than a raw UUID, and it buys three things worth more than the bytes: an ID
is self-describing in a log line or a support ticket; IDs are stable across a dump and restore
into another environment; and allocation needs no database round trip, which matters because
the domain constructs entities before any transaction is open.

Public URLs and API paths use **slugs**, not IDs. `products.slug` is globally unique and
constrained to a kebab-case shape. A slug is immutable after creation, because it is a public
identifier — renaming a product creates an alias, it does not rewrite the slug.

## The rules the schema enforces

### 1. Release history is append-only

There is no `UPDATE` statement against `releases` in the query set, and the table is designed
so none is needed:

- **Withdrawal** sets `withdrawn = true` with `withdrawn_at` and `withdrawn_reason`. The row
  remains queryable. A `CHECK` keeps the boolean and the timestamp consistent, so a withdrawn
  release always records when.
- **Correction** inserts a *new* row with `corrects_release_id` pointing at the original. The
  original is untouched. Both are visible; the API serves the correction and can show the
  chain.
- **Supersession** sets `superseded_by_release_id`, which is a pointer, not a rewrite.
- **Rollback of a bad import** is a bulk withdrawal keyed on `collector_run_id`. That column
  exists on `releases` specifically so that "undo everything that run published" is one
  query. Without it, a bad collector deployment is unrecoverable except by hand.

The `ON DELETE RESTRICT` on `evidence_id` means a release's evidence cannot be deleted while
the release exists. Retention policy cannot quietly orphan a published fact.

### 2. Dates never gain precision they did not have

`release_date` is a `DATE`, paired with `release_date_precision` in
`{exact_day, month_only, year_only, unknown}`. A `CHECK` constraint forces the stored date to
be a canonical anchor:

```sql
CONSTRAINT releases_date_precision CHECK (
    (release_date_precision = 'unknown'    AND release_date IS NULL)
 OR (release_date_precision = 'exact_day'  AND release_date IS NOT NULL)
 OR (release_date_precision = 'month_only' AND release_date IS NOT NULL
         AND EXTRACT(DAY FROM release_date) = 1)
 OR (release_date_precision = 'year_only'  AND release_date IS NOT NULL
         AND EXTRACT(DAY FROM release_date) = 1 AND EXTRACT(MONTH FROM release_date) = 1)
)
```

Storing `2026-02-01` for "February 2026" is not a lie as long as the precision column travels
with it and the API never renders the day. The constraint guarantees the anchor is canonical,
so an application bug cannot produce `2026-02-17` with `month_only` precision and leave a
future reader unable to tell which part was real. `unknown` requires a NULL date outright,
because there is no honest anchor for "we do not know when".

The API presenter is the other half of this: it renders `YYYY-MM-DD` only for `exact_day`,
`YYYY-MM` for `month_only`, `YYYY` for `year_only`, and omits the field entirely for
`unknown`. A consumer cannot parse a fake day out of a FirmScout response.

### 3. Versions are text, and nothing orders them

`raw_version` and `normalized_version` are `TEXT`. There is no numeric column, no
`ORDER BY version` anywhere, and no index that implies an ordering. Both are stored because
the raw string is what the vendor published and the normalised one is what FirmScout matched
on; losing either makes a later dispute unresolvable.

"Latest observed" is a derived flag on `release_product_mappings`, set by `PublishRelease`
from release date, first-observed timestamp, and channel. The partial unique index

```sql
CREATE UNIQUE INDEX release_mappings_latest_idx
    ON release_product_mappings (product_id, COALESCE(channel, ''))
    WHERE is_latest_observed = true AND product_id IS NOT NULL;
```

turns a concurrency bug into a constraint violation. Two simultaneous publications for the
same product and channel cannot both claim to be latest; one transaction fails and retries.

The flag lives on the mapping rather than on the release because "latest" is a property of a
product-and-channel pair. A release shared by forty products may be latest for thirty of them
and superseded for ten.

### 4. Applicability is a mapping table

`release_product_mappings` carries `hardware_revision`, `region`, `channel`,
`deployment_mode`, and an `applicability_note`, and targets either a product or a family
(enforced by a `CHECK` that exactly one is set). This is what lets a single release row apply
to one exact model, several models, a whole family, one hardware revision, or one region,
without duplicating the fact once per product.

No release row targets a family today, and that is a deliberate restriction rather than an
unfinished feature. A family in this catalogue groups devices offered the same base firmware
*image file* — MikroTik's published architecture decides which `routeros-<version>-<arch>.npk`
a device takes — and it does not group them by version: every architecture measured is offered
the same current release. A family-targeted mapping would assert that a specific release
applies to every member, and the "which version" half of that claim is exactly what
measurement declined to support. `release_mappings_family_latest_idx` (migration `00005`)
constrains the first such row anyone writes; `00001`'s equivalent index is partial on
`product_id IS NOT NULL` and never covered family-targeted rows at all. See ADR-0024.

### 5. Evidence is mandatory and self-describing

`releases.evidence_id` is `NOT NULL`. Evidence carries `source_url`, `retrieved_at`,
`content_hash`, `excerpt`, `raw_value`, `normalized_value`, `collector_id`,
`collector_version`, and `discovery_method`. When AI was involved, a `CHECK` requires both
`ai_model_id` and `ai_prompt_version`:

```sql
CONSTRAINT evidence_ai_provenance CHECK (
    discovery_method <> 'ai_assisted' OR (ai_model_id IS NOT NULL AND ai_prompt_version IS NOT NULL)
)
```

`excerpt` must be non-blank. `release_notes.excerpt` is capped at 4000 characters by
constraint, implementing the policy that FirmScout links to release notes rather than
reproducing them.

### 6. Compliance gates dispatch, in an index

`sources` carries `official`, `quality_class`, `robots_policy_status`,
`terms_review_status`, `authentication_type`, and `enabled`. The scheduler's query uses a
partial index whose predicate *is* the dispatch rule:

```sql
CREATE INDEX sources_dispatchable_idx ON sources (next_check_at)
    WHERE enabled = true
      AND health_status IN ('active', 'degraded')
      AND robots_policy_status IN ('allowed', 'not_applicable')
      AND terms_review_status IN ('approved', 'restricted');
```

A scheduler query that omits a compliance predicate does not merely violate policy — it
stops using the index, which makes the omission visible in the query plan. See
[ADR-0018](../adr/0018-source-compliance-policy.md).

### 7. Release type is required and constrained

`releases.release_type` is `NOT NULL` and references `release_types`, a seeded lookup table
with twelve values: firmware, BIOS, BMC firmware, driver, operating system, embedded OS,
application software, SaaS release, management platform, security update, documentation-only,
and unknown. There is no default. A collector must decide, or emit `unknown` and route to
classification. This is the schema-level answer to "do not label every release as firmware".

A lookup table rather than a PostgreSQL `ENUM` because adding a type should be registry data,
not a migration, and because `ENUM` values cannot be removed once added.

### 8. A hardware model is a product, and what it runs is an edge

A fleet's inventory is a list of model numbers, so the catalogue has to be reachable by model
number. It is, without a device table: a device is a `products` row whose `model_identifier`
carries the vendor's published product code, which means it inherits `product_aliases`,
`product_categories`, `product_summaries` and the full-text search path with no parallel
implementation of any of them. No column marks a row as a device — `model_identifier` being
set is the whole test (`domain.Product.IsHardwareModel`), and it is deliberately not exclusive
with having a release stream, because a rack server is a device *and* publishes its own BIOS
versions.

`product_relationships` is the one genuinely new thing: a directed edge from a device to the
operating system whose releases the operator is actually looking for. Its vocabulary has
exactly one member, `runs_os`, because that is the only product-to-product edge with measured
evidence behind it; the `CHECK` is written `IN ('runs_os')` so widening it is one word. The two
foreign keys differ on purpose — `from_product_id` CASCADEs so deleting a device takes its
edges with it, `to_product_id` RESTRICTs so an operating system that devices point at cannot
be deleted out from under them. It carries no `evidence_id`: registry-authored facts are
provenanced by Git and `registry_path` (ADR-0016), and evidence rows are collector artefacts
with a content hash and a collector version that a human's pull request does not have.

The edge is a navigation claim — "the firmware for this box is published over there" — and
explicitly not an applicability claim. A device holds zero `release_product_mappings` rows, so
it has no latest release of its own and `/products/{slug}/latest` answers 404. See ADR-0024.

## Table-by-table notes

### `sources`

The busiest table conceptually, holding four groups of fields: identity and scope, authority
and compliance, collection configuration, and change-detection state.

Scope is expressed by `product_id`, `product_family_id`, and the `source_products` join
table. A `CHECK` forbids setting both scalar columns. Three shapes are supported: a source
covering one product, a source covering a family, and a vendor-wide catalogue with both null
whose applicability is resolved at extraction time. `source_products` handles the fourth and
commercially most valuable shape — one catalogue page explicitly covering forty products,
fetched once.

Change-detection state (`etag`, `last_modified_value`, `normalized_content_hash`,
`consecutive_unchanged`, `consecutive_failures`, `retry_after_until`, `next_check_at`) lives
on the source rather than in a separate table because it is small, always read together, and
always written together at the end of a check.

`health_status` implements the source state machine. `relocated_to_source_id` records where a
moved source went, which is what makes the repair path auditable.

### `source_artifacts`

Content-addressed, with `content_hash` unique. An unchanged source produces no new artifact —
only a new `source_checks` row pointing at the existing one. Since the overwhelming majority
of checks find no change, this is the single largest storage saving in the system, and it is
structural rather than a cleanup job.

`retention_class` and `expires_at` drive lifecycle. `reference_count` is maintained by the
application; the honest caveat is that it can drift, and the deletion policy is deliberately
conservative because deleting an artifact still cited by evidence is worse than retaining
rubbish.

### `candidate_releases`

The quarantine between observation and fact. `product_match_status` distinguishes
`unresolved`, `unique`, `ambiguous`, and `no_match` — an ambiguous match is never guessed; it
becomes a review item.

`dedupe_key` is unique per source and is the most dangerous field in the schema for a
collector author. Computed inconsistently between runs, it produces duplicate candidates;
computed too coarsely, it silently swallows genuine releases. The SDK provides the default
implementation for this reason.

`state` implements the candidate state machine and is checked against the eleven declared
values, so an invalid state cannot be written even by a buggy adapter.

### `product_summaries`

The denormalised projection the public site and search read. One row per product, refreshed
by `PublishRelease` and by `SyncRegistry`. It carries a `GENERATED ALWAYS AS ... STORED`
`tsvector` combining product name (weight A), vendor name and aliases (B), and family name
(C), indexed with GIN, plus a `pg_trgm` index on the product name for typo tolerance.

This is where the cost-per-search target is met: a product page and a search result are one
indexed read, not a six-way join. The trade-off is a real staleness risk, which is why the
refresh belongs inside the publication transaction rather than in a background job.

`SyncRegistry` is the second writer because a product that never reaches the publish path has
no row here at all, and a missing row is not a stale value — it is a 404 on the public API and
absence from search. Every hardware model is in exactly that position, having no releases of
its own, so a sync that upserted products without refreshing them would produce a catalogue
nobody could read.

`model_identifier` and `runs` (migration `00005`) are display columns. `runs` mirrors
`official_sources`: a JSONB array of `{slug, name, kind}` built by a `LATERAL`, so a device
page stays one indexed read. `model_identifier` is deliberately *not* part of the generated
search vector — a device is found by its model number through a `model_number` alias, which is
already flattened into `aliases_text` at weight B, and regenerating a `GENERATED ALWAYS` column
to index a string the aliases already index would buy a duplicate. The order matters when both
writers run: a summary rebuilt before a product's relationships are written records `runs` as
empty, which is why `SyncRegistry` refreshes summaries in its final pass.

### `jobs`

The `JobQueue` port's PostgreSQL adapter ([ADR-0015](../adr/0015-job-queue-port.md)).
`idempotency_key` is unique, which is what makes "enqueue this check" safe to call twice.
`trace_context` carries W3C trace context so a trace survives the queue hop — the place
distributed traces are usually lost.

Dequeue is `SELECT ... FOR UPDATE SKIP LOCKED` over the partial index on
`(priority, run_after)`. `locked_until` provides lease expiry so a crashed worker's jobs
return to the pool. `status = 'dead'` with `dead_lettered_at` is the logical dead-letter
queue.

### `api_keys`

Stores `key_hash` (SHA-256 of the secret) and a 4-to-16 character `key_prefix` for
identification. The plaintext is displayed once at creation and never stored. The `rotating`
status supports an overlap window during rotation. Logs and traces carry the prefix only,
enforced in the telemetry redaction layer rather than at each call site.

### `usage_records` and `usage_aggregates`

Records are the source of truth, with `idempotency_key` unique so a retried request cannot be
counted twice. Aggregates are a derived rollup that quota enforcement reads, because scanning
raw records on every request would put the meter in the latency path. The accepted
consequence is that enforcement may lag by one aggregation window, allowing slight overage at
a quota boundary.

### `ai_runs`

Records every agent invocation whether or not it succeeded: trigger reason, input artifacts,
prompt version, model id, token counts, estimated cost, the structured output, whether that
output passed schema validation, the outcome, and any human decision. Cost control depends on
this table being written even for failed runs — an agent that fails schema validation has
still spent tokens, and a budget that only counts successes is not a budget.

## Deferred to later migrations

Specified here, not created by `00001_initial.sql`. They are deferred because the MVP does
not implement CVE correlation or lifecycle tracking, and creating unused tables invites
premature commitment to a shape that field experience will change.

### `security_advisories`

`id`, `vendor_id`, `advisory_id` (the vendor's own identifier), `title`, `summary`,
`canonical_url`, `severity`, `cvss_vector`, `cvss_score`, `published_date`,
`published_date_precision`, `updated_date`, `source_id`, `evidence_id`, `created_at`.

### `cves`

`cve_id` (primary key, e.g. `CVE-2026-12345`), `published_at`, `last_modified_at`,
`description`, `cvss_vector`, `cvss_score`, `cwe_ids`, `references`, `state`
(`published`, `reserved`, `rejected`, `disputed`), `raw_record` JSONB.

### `cve_product_mappings`

The subsystem the brief is emphatic about. `cve_id`, `product_id`, `advisory_id`,
`cpe_uri`, `affected_version_range`, `fixed_in_version`, `hardware_revision`,
`deployment_mode`, and `status` in
`{confirmed_affected, confirmed_not_affected, potentially_affected, unknown, fixed_in_version, vendor_investigation_pending}`,
plus `evidence_id`, `confidence_score`, `matched_by`
(`vendor_advisory`, `cpe_match`, `manual`, `ai_proposed`), and `reviewed_by`.

A `CHECK` will require that `status = 'confirmed_affected'` is reachable only when
`matched_by` is `vendor_advisory` or `manual` — text similarity and CPE inference alone can
never produce a confirmed status. That constraint is the schema-level expression of the rule
that applicability is never inferred from similar text.

### `lifecycle_events`

`product_id`, `event_type` (`general_availability`, `end_of_sale`, `end_of_software_support`,
`end_of_security_support`, `end_of_life`, `end_of_service`), `event_date`,
`event_date_precision`, `announced_date`, `source_id`, `evidence_id`, `superseded_by_product_id`.

### `user_corrections`

`subject_type`, `subject_id`, `submitted_by`, `contact`, `claim`, `evidence_url`,
`evidence_excerpt`, `state` (`submitted`, `triaged`, `accepted`, `rejected`, `duplicate`),
`triage_category` (`registry_wrong`, `extraction_wrong`, `vendor_page_wrong`,
`already_correct`), `resulting_release_id`, `resolution_note`, `attribution_name`,
`reviewed_by`, timestamps.

### Partitioning

`source_checks`, `source_artifacts`, `usage_records`, and `analytics_events` are the
high-growth tables. They are shaped for monthly range partitioning on their timestamp column
but are not partitioned in the MVP, because partitioning an empty table is a guess about
volumes nobody has measured. The trigger to partition is in the scaling thresholds table in
[cost-controls.md](cost-controls.md).

## The queries this model exists to answer

Each of these is a single indexed query, which is the test of whether the model is right.

| Question | How |
| --- | --- |
| What is the latest observed version? | `product_summaries` by `product_id` — one row read |
| What is the latest *recommended* version? | `releases` joined through mappings where `recommended = true`; **NULL is a valid answer** and is returned as such rather than substituting the newest |
| What versions are known for this product? | `release_product_mappings` joined to `releases`, ordered by `release_date DESC NULLS LAST, first_observed_at DESC` — never by version string |
| Which release was considered latest on date D? | The newest mapped release with `first_observed_at <= D`, excluding rows withdrawn on or before D |
| When was this release first observed? | `releases.first_observed_at` |
| Which source supports this fact? | `releases.evidence_id` → `evidence.source_url`, `retrieved_at`, `content_hash`, `excerpt` |
| Was this release withdrawn? | `releases.withdrawn`, with `withdrawn_at` and `withdrawn_reason` |
| Which products share this release? | `release_product_mappings` by `release_id` |
| I have a model number stamped on a chassis — what is it? | `product_summaries.search_vector` via the `model_number` alias flattened into `aliases_text` — the same single indexed read every other search uses |
| What operating system does this device run? | `product_summaries.runs`, precomputed — no join at read time |
| Which release applies to this exact model? | **Not answerable, and stated as such.** A device holds no `release_product_mappings` rows, so the API returns `firmwareApplicability.basis = runs_os_unverified` and a 404 from `/latest` rather than substituting the operating system's newest release. The sibling member `ownReleases {mapped, releaseCount}` answers the *other* question — whether the releases in the response are this product's own — because a product may be a device **and** its own release stream at once, and one scalar had room for only the winner of that test (ADR-0024, 2026-09-06 amendment) |
| Which sources are due for a check? | `sources_dispatchable_idx` ordered by `next_check_at` |
| What is this consumer's usage this month? | `usage_aggregates` by consumer and period |

## What is not in the schema, on purpose

- **No soft-delete flags on registry tables.** Registry rows are removed by removing the YAML
  and running sync. `ON DELETE RESTRICT` on the paths that would orphan facts prevents the
  destructive case.
- **No `updated_at` triggers.** Timestamps are set by the application, which owns the
  transaction and knows whether a write was a meaningful change. Triggers would fire on
  no-op updates and hide logic from the code.
- **No stored procedures containing business rules.** Business logic hidden in SQL is one of
  the explicit anti-patterns in [ADR-0002](../adr/0002-clean-architecture.md). The database
  enforces *invariants*; the application enforces *policy*.
- **No `ORDER BY` on any version column**, anywhere, ever.
