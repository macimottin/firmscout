# ADR-0004: sqlc + pgx/v5 for data access, no ORM

- **Status:** Accepted
- **Date:** 2026-09-03
- **Deciders:** founding team
- **Requires qualified legal review:** no
- **Related:** ADR-0002, ADR-0003

## Context

FirmScout's PostgreSQL adapter needs to translate hand-written, PostgreSQL-feature-using SQL (`SKIP LOCKED`, `tsvector` queries, `JSONB` operators, `CHECK`-constrained enums) into Go types, while keeping the domain entities in `internal/domain` free of any persistence-framework concept (ADR-0002: an adapter converts its library's errors and types at the boundary; `pgx.ErrNoRows` never reaches a use case). The candidates are, broadly, a code-generation tool that compiles hand-written SQL against the real schema, a full ORM with struct-tag-driven mapping and often its own query builder or migration DSL, or hand-written `database/sql`/`pgx` calls with manual scanning.

The project's stated priority — a small, auditable dependency tree, since security posture depends on it (§3.2) — and the Clean Architecture rule that domain entities carry no persistence annotations both bear directly on this choice.

## Decision

FirmScout uses **sqlc** to generate Go code from hand-written SQL query files (`database/queries/*.sql`) against the schema defined by the goose-format migrations in `database/migrations/`, and **pgx/v5** as the underlying PostgreSQL driver and connection pool. sqlc's generated types are used only inside `internal/adapters/postgres` — repository implementations translate sqlc row types into `internal/domain` entities at the boundary, and never the reverse. Domain entities carry no struct tags, no ORM annotations, and no knowledge that PostgreSQL exists.

Query files are reviewed as SQL, in SQL, by anyone who can read SQL — including non-Go contributors proposing a new query for a collector or a registry lookup. `sqlc generate` runs in CI (`sqlc diff`, per the blueprint's B8 quality gates) and fails the build if generated code is stale relative to the query files, so a query change without a regenerate is caught before merge, and a query that does not type-check against the actual schema fails at build time rather than at runtime.

## Consequences

### Positive

- Every query is checked against the real schema at generate time: a typo'd column name, a type mismatch, or a query referencing a dropped table fails `sqlc generate` in CI, not a production request.
- SQL stays SQL — `SKIP LOCKED`, window functions, `tsvector @@ plainto_tsquery`, and `JSONB` operators are written directly and reviewed as what they are, with no query-builder DSL translating intent into SQL a reviewer then has to mentally re-derive.
- No reflection-based struct mapping at runtime, no ORM lazy-loading surprises (an accidental N+1 query hidden behind a property access), and no ORM-specific migration or seeding conventions to learn.
- Domain entities stay exactly what ADR-0002 requires: plain Go types with no persistence framework's fingerprints on them, because sqlc's generated types are adapter-local and never imported by `internal/domain` or `internal/application`.
- The generated code is committed, so a reviewer can read the exact SQL that will run without invoking a code generator, and CI catches drift if someone edits generated code by hand or forgets to regenerate.

### Negative

- sqlc's static analysis of SQL is not infallible for every advanced PostgreSQL construct (recursive CTEs and some dynamic constructs occasionally need workarounds or `sqlc.arg`/`sqlc.narg` annotations); a small number of queries may need to be structured around sqlc's limitations rather than written in the most natural form.
- Query files and generated code add a build step contributors must run (`sqlc generate`) and a CI check that can produce a confusing failure ("generated code is stale") if a contributor edits a query without regenerating; this needs to be documented clearly in the contribution guide.
- Compared to an ORM's associations and eager/lazy loading, composing a complex read (e.g., a product page needing releases, evidence, and vendor data) requires either several targeted queries assembled in the repository or a hand-written join query — there is no framework doing this automatically, which is more code, even if it is more predictable code.
- sqlc is a smaller, less universally known tool than the major ORMs; a contributor's first PR touching persistence has a short learning curve specific to this project's tooling.

### Neutral

- This decision does not change if the database engine ever changed (it will not, per ADR-0003) — sqlc is tied to the SQL dialect, not to an abstract portability goal. The Go interface (`Querier`) sqlc generates happens to also serve as a natural seam for the repository port, but that convenience is incidental, not the reason sqlc was chosen.

## Alternatives considered

### GORM (or a comparable full-featured ORM)

Rejected. GORM's struct-tag-driven model would pull persistence concerns into whatever struct it operates on, creating pressure to either duplicate domain entities as GORM-tagged persistence models (adding a mapping layer sqlc avoids) or let GORM tags leak into domain types (violating ADR-0002 directly). GORM's implicit query generation and lazy loading also make the exact SQL executed harder to review at a glance, which cuts against the project's auditability priority.

### ent (Meta's entity framework)

Rejected. ent generates a strongly-typed graph API from a schema defined in Go, which is elegant but inverts the relationship FirmScout wants: the SQL migrations are the source of truth for the schema (goose format, hand-written, reviewed as SQL), not a Go schema DSL that generates migrations. ent's code-generation model is also heavier and less transparent to a contributor who just wants to read the SQL that will run.

### sqlx (or hand-written `database/sql`/pgx with manual struct scanning)

Rejected as the primary approach, though it is the closest alternative in spirit. sqlx removes the compile-time schema check that is sqlc's main value: a renamed column or a mismatched scan target is a runtime error discovered by a test (if one exists) or in production, not a build failure. Given the volume of queries FirmScout will accumulate across catalogue, sourcing, ingestion, and entitlement tables, the cost of losing that compile-time check outweighs the marginal simplicity of skipping a code generator.

## Revisit when

- sqlc's limitations force workarounds on a large enough fraction of new queries (a qualitative signal, tracked via contributor friction reports) that hand-written SQL with a thin scanning helper would be simpler for the team to maintain.
- A read pattern emerges that is genuinely graph-shaped (deep, variable-depth joins driven by user-selected fields) where an ORM's or ent's approach would measurably reduce repository code without compromising the compile-time-checked guarantee this ADR is built on.
