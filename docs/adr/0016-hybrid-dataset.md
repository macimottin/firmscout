# ADR-0016: Hybrid dataset — registry in Git, observed facts in PostgreSQL

- **Status:** Accepted
- **Date:** 2026-09-03
- **Deciders:** founding team
- **Requires qualified legal review:** no
- **Related:** ADR-0003, ADR-0009, ADR-0018

## Context

The brief asked whether FirmScout's dataset should live in Git or in PostgreSQL, as an either/or choice. That framing conflates two kinds of data with genuinely different properties. **Curated intent** — which vendors exist, which products are tracked, which sources are official, how to parse each source — changes rarely, benefits enormously from code review, pull-request-based collaboration, blame history, and offline diffing, and is exactly the kind of data an open-source contributor (assumption P5) should be able to propose changes to without needing database access or infrastructure credentials. **Observed facts** — releases, source checks, extraction candidates, artifacts, API usage — are high-volume, machine-generated, append-only, and need to be queried efficiently at request time (§11 items 2–3). Forcing both into a single store fails in both directions: a Git-only dataset cannot answer "what is the latest observed version" efficiently at request scale, and a PostgreSQL-only dataset makes contributing a new vendor require database access, defeating the pull-request contribution model the project depends on.

## Decision

The dataset is **hybrid**, split along the curated-intent/observed-fact line, per §3.3:

- **Git** (`dataset/` and `collectors/config/`) holds vendors, product families, products, aliases, categories, source definitions, and collector configurations as **YAML**, validated against **JSON Schema in CI** (`schemas.yml`), and synchronised into PostgreSQL by the `firmscout registry sync` CLI command. This is the only path by which registry data enters the database.
- **PostgreSQL** holds everything observed: releases, evidence, source checks, artifacts, candidate releases, validation results, review items, API usage, and audit events — high-volume, query-heavy, and never suited to Git's diff-and-review model at this scale.
- **Exported snapshots** are periodic public data dumps generated *from* PostgreSQL, published under the dataset licence (ADR-0009), giving the community a way to consume the observed data set without database access, while keeping the observed data itself in the store built to serve it efficiently.

Registry tables (`vendors`, `product_families`, `products`, `product_aliases`, `categories`, `sources`, `collector_definitions`) carry a `managed_by` column and a `registry_path`, distinguishing rows synchronised from Git from any row created through an admin path, so the two provenances never become ambiguous in the database itself (§11 item 1). The known failure mode — **registry drift**, where someone edits a registry table directly in PostgreSQL, bypassing Git — is mitigated by making `firmscout registry sync` the **only writer** of `managed_by = 'registry'` rows; any other write path to those tables is treated as a bug or an explicit admin override that must itself be tracked.

## Consequences

### Positive

- A contributor adds a new vendor, product, or source with a pull request against YAML files — no infrastructure, no database credentials, no deployment access — which is precisely the low-friction contribution path assumption P5 needs to hold for collector coverage to scale beyond the founder-generated pilot dataset.
- The platform answers catalogue and release queries in milliseconds against PostgreSQL, because observed, high-volume data never has to be reconstructed from a Git-stored format at request time.
- The registry is diffable and revertible: a bad vendor definition, a typo'd source URL, or an incorrect collector config change is a normal Git revert, with full blame history showing who proposed what and when, and CI schema validation catching structural errors before merge rather than after.
- Observed data is never in a merge conflict — releases, evidence, and source checks are generated by the system itself, not hand-edited by multiple contributors simultaneously, so the two stores' different collaboration models fit their respective data's actual access patterns.
- The `managed_by` / `registry_path` provenance columns make it possible to answer "did this row come from Git or was it created another way" as a simple query, rather than requiring institutional memory or a separate audit log lookup.

### Negative

- Registry drift is a real, named risk (§3.3): if someone edits a registry-managed row directly in PostgreSQL (via a manual `UPDATE`, an ad hoc admin script, or a future admin UI that is not built carefully) without going through Git, that row's next `registry sync` will either silently overwrite the manual change or the schema will let it diverge, and neither project state (drifted-and-unnoticed, or overwritten-and-unnoticed) is good. The `managed_by` marker and "sync is the only writer" rule are policy enforced by convention and code review at this stage, not yet by a database-level constraint preventing any other writer.
- Two stores for one conceptual dataset means two places to look when debugging "why does this product page show the wrong vendor" — is the registry YAML wrong, did sync fail, or is the PostgreSQL row stale relative to a more recent sync — adding a diagnostic step that a single-store design would not have.
- `firmscout registry sync` becomes a load-bearing, correctness-critical piece of infrastructure: a bug in the sync logic (a partial sync, a schema-validation gap, an incorrect upsert) can silently desynchronise the two stores, and this needs its own test coverage and idempotency guarantees to be trustworthy.
- JSON Schema validation in CI catches structural errors in the YAML (missing required fields, wrong types) but cannot catch semantic errors (a source URL that is syntactically valid but points to the wrong page, a collector config that is well-formed but wrong) — those still require human review and, ideally, the fixture-based collector testing described in ADR-0005.

### Neutral

- The dataset's actual growth pattern (how large `dataset/` gets as vendor coverage scales) will determine whether Git's performance characteristics remain comfortable — this is not expected to be a problem at the scale of hundreds or low thousands of vendors, but is not something this ADR has measured.
- Categories are explicitly registry data, not code (§4.4), meaning adding a new product category (e.g., "power and UPS equipment") is a YAML change under this same hybrid model, not a schema migration or code change — this reinforces the dataset design's stated goal of making curated intent something a non-programmer contributor can propose.

## Alternatives considered

### Dataset entirely in Git, PostgreSQL used only as a build/query cache regenerated from Git

Rejected. This would need to treat every observed fact (releases, evidence, source checks) as something ultimately traceable back to a Git commit, which is nonsensical for machine-generated, continuously arriving data — there is no meaningful "pull request" for a source check that ran at 3am, and reconstructing query performance comparable to PostgreSQL from a Git-stored format at read time is not a reasonable ask.

### Dataset entirely in PostgreSQL, with an admin UI for curating vendors, products, and sources instead of Git

Rejected. This removes the pull-request review model that makes registry changes reviewable, diffable, and revertible with standard, already-understood tooling (Git, GitHub PR review), and it re-introduces exactly the contribution friction (needing database or admin-UI access) that the hybrid design is built to avoid. It would also make community-authored collector configs harder to review as a unit alongside the source definition and product mapping they depend on.

### A third-party headless CMS or config-management system for the registry, instead of plain YAML in Git

Rejected. This would add an external dependency and a proprietary or semi-proprietary format for data that is well served by plain YAML validated against an open JSON Schema — introducing a CMS would not solve a problem this design has, and would work against the project's stated preference for a small, auditable, self-hostable stack.

## Revisit when

- Registry drift is observed in practice (a registry-managed row found to have diverged from its Git source without going through sync), at which point database-level enforcement (e.g., triggers rejecting direct writes to `managed_by = 'registry'` rows, or role-based permissions restricting write access to the sync process) should be added rather than relying on convention alone.
- `dataset/` grows large enough that Git operations (clone, diff, CI schema validation) measurably slow down contributor workflows, at which point either splitting the registry across multiple repositories or a different curation mechanism should be evaluated.
- `firmscout registry sync` failure modes (partial syncs, validation gaps) are observed in production with enough frequency to warrant a more robust reconciliation mechanism (e.g., a dry-run diff mode, or transactional all-or-nothing sync semantics) beyond what exists today.
